# Database (PostgreSQL)

PostgreSQL is the source of truth for users and videos (RT1). The schema is
created and evolved only by versioned migrations; this file and
[`db/migrations/`](../db/migrations/) are the database creation script of
deliverable **D2**.

## Migrations

- Tool: [goose v3](https://github.com/pressly/goose) (library only, no CLI to
  install). Files are plain SQL named `NNNNN_description.sql`, each with a
  `-- +goose Up` and a `-- +goose Down` section. goose records the applied
  versions in the table `goose_db_version`.
- The files are embedded in the api binary (`db/migrations/migrations.go`,
  `embed.FS`), so the image that serves the API also carries its schema.
- `api migrate` applies every pending migration and exits
  (`postgres.Migrate`). It holds a PostgreSQL advisory lock while running,
  so concurrent runs are safe, and it is idempotent: with nothing pending it
  only reports the current version.

### How they run

| Where | How |
|---|---|
| Compose stack (`make up`, integration tests) | The one-shot service `migrate` (api image, command `migrate`) runs after `postgres` is healthy. `api` has `depends_on: migrate: condition: service_completed_successfully`, so it never starts against an old schema. |
| Compose stack, on demand | `make migrate` (`docker compose run --rm --build migrate`). |
| From the host | `DATABASE_URL=postgres://video:video@localhost:5432/video_processor?sslmode=disable go run ./cmd/api migrate` |
| Kubernetes (Phase 4) | The same image and command as a `Job` or an init container. |

`api migrate` only needs `DATABASE_URL` (and optionally `LOG_LEVEL`).

### Adding a migration

Add `db/migrations/0000N_what_it_does.sql` with the next number, never edit
a migration that was merged, and make the `Down` section undo the `Up`.

## Schema (version 2)

```sql
CREATE TABLE users (
    id            uuid        PRIMARY KEY,           -- generated by the api
    name          text        NOT NULL,              -- 1..100 characters
    email         text        NOT NULL,              -- lowercased (CHECK)
    password_hash text        NOT NULL,              -- bcrypt
    created_at    timestamptz NOT NULL
);
CREATE UNIQUE INDEX users_email_key ON users (email);

CREATE TABLE videos (
    id            uuid        PRIMARY KEY,           -- generated by the api
    user_id       uuid        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    original_name text        NOT NULL,              -- as uploaded
    storage_key   text        NOT NULL,              -- object key of the video
    zip_key       text,                              -- set when DONE
    status        text        NOT NULL,              -- PENDING | PROCESSING | DONE | FAILED
    frame_count   integer,                           -- > 0, set when DONE
    error_message text,                              -- non-empty, set when FAILED
    created_at    timestamptz NOT NULL,
    updated_at    timestamptz NOT NULL
);
CREATE INDEX videos_user_created_idx ON videos (user_id, created_at DESC, id DESC);
CREATE INDEX videos_status_idx ON videos (status);
```

Version 2 adds the transactional outbox
([ADR 0004](adr/0004-transactional-outbox.md)): the api inserts a video and
the message that queues its processing in the same transaction, and a relay
publishes the messages to RabbitMQ and deletes each row once the broker
confirms it.

```sql
CREATE TABLE outbox (
    id           bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- publish order
    message_id   text        NOT NULL,             -- AMQP message-id (the video id)
    topic        text        NOT NULL,             -- routing key, e.g. video.uploaded
    payload      jsonb       NOT NULL,             -- message body
    created_at   timestamptz NOT NULL DEFAULT now(),
    attempts     integer     NOT NULL DEFAULT 0,   -- failed publishes so far
    last_error   text,                             -- why the last publish failed
    available_at timestamptz NOT NULL DEFAULT now() -- next attempt (backoff)
);
CREATE INDEX outbox_available_idx ON outbox (available_at, id);
```

The exact DDL, with all constraints, is in
[`00001_create_users_and_videos.sql`](../db/migrations/00001_create_users_and_videos.sql)
and [`00002_create_outbox.sql`](../db/migrations/00002_create_outbox.sql).
Notes:

- **E-mails** are unique case-insensitively because the api stores them
  lowercased and a `CHECK (email = lower(email))` enforces it; a duplicate
  hits `users_email_key` (SQLSTATE 23505), which the repository reports as
  `app.ErrEmailTaken` (HTTP `409 email_taken`).
- **Video invariants** of `domain.Video` are also `CHECK` constraints: `zip_key`
  and `frame_count` are set exactly when `status = 'DONE'`, and
  `error_message` exactly when `status = 'FAILED'`. The repository stores the
  zero values of those fields as `NULL`.
- **Listing** (`GET /api/v1/videos`) reads `videos_user_created_idx`: the
  caller's videos newest first, `id` as tiebreak. Page and total come from one
  statement.
- **Timestamps** are `timestamptz` with microsecond precision; the api
  truncates its clock to microseconds before inserting, so what it returns is
  what a later read returns.
- **Status changes** by the worker are conditional
  (`UPDATE videos ... WHERE id = $1 AND status IN (...)`): `PENDING` or
  `PROCESSING` → `PROCESSING` (a redelivered job restarts), `PROCESSING` →
  `DONE`, `PENDING` or `PROCESSING` → `FAILED`. A final video never changes,
  whatever the order or number of deliveries of its job.
- **Outbox relay**: `SELECT ... WHERE available_at <= now() ORDER BY id
  LIMIT n FOR UPDATE SKIP LOCKED`, publish with confirms, then `DELETE` the
  confirmed rows and push the others' `available_at` back (1 s, 2 s, 4 s …
  up to 15 s), all in one transaction. Pending jobs:
  `SELECT count(*), max(attempts), min(created_at) FROM outbox;`

## Repository tests

The repositories (`internal/adapters/postgres`) have integration tests
against a real database. They are skipped unless `POSTGRES_TEST_URL` is set,
apply the migrations themselves and only add rows with fresh ids, so any
database works. The outbox tests create (and drop) a throwaway database next
to it, so a running api's relay does not claim their rows:

```sh
make up
POSTGRES_TEST_URL='postgres://video:video@localhost:5432/video_processor?sslmode=disable' \
  go test -race -count=1 ./internal/adapters/postgres/...
make down
```
